# company-site

A corporate marketing site for a fictional B2B infrastructure company, with a
working contact form and the crawler routes a public site needs.

The point of this example is the two halves of a public-facing site that a
headless CMS is usually bought for: editorial pages an author changes without a
deploy, and a form a stranger can post to. Both go through the engine. Neither
lets the browser near it.

## What it proves

**A form stored in the engine, on the forms preset.** `pnpm run setup` applies
the schema plugin's forms preset with `POST /api/admin/schemas/presets/forms`,
which creates two content types: `forms` (name, a unique slug, the layout as
JSON, a notify address, an active flag) and `form_submissions` (the form as a
relation, the posted data as JSON, a status of `new`, `read` or `spam`). The
contact form is a `forms` record whose layout carries its fields, labels,
bounds, submit text and success message, and the page renders whatever that
record says. Change a label or add an option in the engine and the page changes
on the next request.

**The preset is tables, and the rest is this app.** There is no submit route, so
the form action writes a `form_submissions` record through
`POST /api/admin/content` with this app's credential. Nothing in the engine
reads the layout, so the required fields, the length bounds, the address shape
and the options of a select are checked in `src/lib/server/forms.ts` before the
write. The submission's `status` is required and has to be sent: the preset
declares `new` as its default, but a write that leaves it out is refused as
missing.

**Spam protection is a honeypot this app runs.** The layout sets `honeypot`, the
page renders a field named `_website` that a person never sees, and a filled one
gets the ordinary success message while nothing is stored, so a bot cannot tell
it was caught.

**Public-facing SEO built from content.** `/sitemap.xml` and `/robots.txt` are
generated by the app from the same reads the pages render from, so a role that
closes leaves the sitemap on the next request. Every page carries a title, a
meta description, a canonical URL and Open Graph and Twitter tags derived from
its own fields.

**Content patterns worth copying.** A `belongs_to` relation from an opening to
its hiring manager, populated in one request instead of an N+1. `filters[col]`
for the careers department filter and the footer's page section, which is the
only server-side narrowing the engine has. An app-side sort, because the engine
has none. A layout-level server load for chrome that is content rather than
markup. And a `/[slug]` route so a new marketing page is a write, not a deploy.

## Which sitemap this uses, and why

The flow plugin ships `seo-sitemap` and `seo-robots` templates, which answer
from a `pages` type and a `robots_rules` type.

This example serves its own `/sitemap.xml` instead. A sitemap kept as a
separate list of URLs never sees the content, so it cannot know
that a job closed, a page was renamed or a slug changed, and it has no idea
which routes this app decided to serve any of it from. Every one of those goes
wrong quietly: a sitemap full of URLs that 404 costs crawl budget on every
sweep and nothing reports it. Generating it from `pages()` and `openings()`, the same
functions the pages themselves call, means the sitemap cannot disagree with the
router.

The templates earn their place on an install where crawl rules are an
operations concern edited without a deploy, or where several apps share one
sitemap. That is a real case, just not this one. The same reasoning applies to
`/robots.txt`, where the only line that matters is the pointer at a sitemap this
app serves.

## Content types

All three are prefixed, because every example in this repo shares one engine.

| Type | Fields |
|---|---|
| `site_pages` | `title`, `slug`, `section`, `summary`, `body`, `hero_media_id` |
| `site_team` | `title` (the person's name), `slug`, `role`, `location`, `bio`, `photo_media_id`, `sort_order` |
| `site_openings` | `title`, `slug`, `location`, `department`, `employment_type`, `summary`, `body`, `sort_order`, `hiring_manager` (belongs_to `site_team`) |

## Routes

| Route | What it does |
|---|---|
| `/` | The `home` page entry, plus the first three roles in the site's order |
| `/about` | The `about` page entry, plus the whole team |
| `/careers` | Open roles, filterable by `?department=` |
| `/careers/[slug]` | One role with its hiring manager populated |
| `/contact` | The form definition, rendered. Posts to its own action |
| `/[slug]` | Any other `site_pages` entry, such as `/security-and-compliance` |
| `/media/[id]` | Proxies media bytes, because the engine's download route needs a token |
| `/sitemap.xml` | Generated from this app's content |
| `/robots.txt` | Crawl rules and the sitemap pointer |

## What this example does not do, because the product does not

- **There is no anonymous read.** Every content and schema route sits behind
  auth, so no page here can be rendered by the browser. This app is a
  backend-for-frontend and the credential never leaves the server. That is not a
  stylistic choice.
- **The contact form has no anonymous route either.** Reading the form,
  writing a submission and listing submissions all need a credential, so the
  form posts to this app's own action and the app writes the record.
- **No JSON-LD.** The app ships the repo's `script-src 'self'` policy, and
  browsers apply `script-src` to inline `<script type="application/ld+json">`.
  SvelteKit's CSP handling only nonces the scripts it generates itself, not ones
  written in `<svelte:head>`, so structured data would need a relaxed policy or
  a nonce the framework does not expose.
- **No sort parameter anywhere.** The engine always returns rows `created_at
  DESC` and ignores `sort`, `order` and `fields` without complaining. The
  running order of the team and the roles is stored in a `sort_order` field and
  applied by the app.
- **Filters are exact equality only.** `filters[department]=Security` works.
  There is no `LIKE`, no range, no `IN`, and no way to ask for two departments
  at once. A misspelled department returns an empty list rather than an error.
- **`limit` is clamped to 25..200.** Asking for three rows returns twenty five.
  The shared helper slices for you when you ask for fewer. The careers teaser on
  the home page reads the whole list, sorts it and takes three, because it needs
  the site's own order rather than the newest three.
- **No rate limit and no duplicate window per visitor.** The engine sees one
  caller, this app, and nothing in the preset counts submissions. A site with a
  public form in production puts a limit in front of this action.
- **Notification mail is not sent.** The flow plugin's `form-submitted`
  template mails a new submission to the form's `notify_email` from a flow on
  `form_submissions` after_create. It needs the `flow-pro` capability and a mail
  sender, so the seed leaves `notify_email` empty rather than pretending.
- **Submissions are only visible in the engine.** There is no page here that
  lists them. They are `form_submissions` records: read them in the admin UI or
  with `GET /api/v1/content/form_submissions` and a token.
- **The hiring manager relation is optional.** `belongsTo()` declares
  relations optional, so a missing hiring manager is handled in the app.
- **The seed uploads no images.** `hero_media_id` and `photo_media_id` are real
  fields and `/media/[id]` is a real route, but nothing populates them, so the
  site renders without images until you upload some through the admin UI and
  paste the ids in.
- **Page bodies are plain text**, split on blank lines. They are rendered as
  paragraphs, never with `{@html}`. The engine will store markup happily. This
  app will not inject it.

## Running it

The shared engine has to be up first. From the repo root:

```
make up
pnpm install
```

Then, in this app:

```
pnpm run setup     # content types, the forms preset, the contact form, the seed
pnpm dev       # http://localhost:5175
```

`pnpm run setup` is safe to run again. Applying a content type that already exists
is accepted, a preset whose types exist answers 409 and is taken as done, the
contact form is only created when its slug is free, and each
seeded record is skipped when something already holds its slug, so a run that
fails half way through can just be repeated.

Worth opening after the seed:

- `http://localhost:5175/careers?department=Infrastructure` for the engine-side
  filter
- `http://localhost:5175/sitemap.xml` for the generated document
- `http://localhost:5175/contact`, submitted with a field left empty, for the
  app's own validation
- the admin UI at `http://localhost:4401`, where the submission you just sent is
  a `form_submissions` record
